# Foundation crates

SimOxide and its [QVTo engine](../qvto/) share two layers that both need: Java's behaviour, and
EMF. The shared crates are in `crates/foundation/`. Before the merge, each side had its own
copies: three of `Double.toString`, two of FxHash and of the `HashMap` order, two object graphs
and two XMI loaders.

| Crate | Licence | Contents |
|---|---|---|
| `simoxide-jcompat` | EPL-2.0 | Java behaviour that the Java SE documentation specifies: `String.hashCode` and the boxes' hash codes, `Double.compare` (`hash`); `Double.toString` and `Float.toString` of JDK 19 and later, writing into a byte buffer without allocation (`fmt`); `Integer.parseInt`, `Long.parseLong` and `Double.valueOf` with Java's syntax (`parse`); `Character` data generated by running JDK 21 (`chars`); `Math.round`, `max`, `min` (`math`); the `MapOrder` interface with `LinkedHashMap`'s insertion order (`order`); the Fx hasher (`fx`) |
| `simoxide-jcompat-exact` | **none granted** (opt-in) | what only OpenJDK's and HotSpot's sources define: `java.util.HashMap`/`HashSet` iteration order with resizes, tree bins and removal (`hashmap`), its closed form for insert-only maps (`order::JdkHashOrder`), HotSpot's identity-hash generator with the recovery of a thread's sequence (`hotspot`) |
| `simoxide-hotspot-math` | GPL-2.0-only (opt-in) | a port of HotSpot's x86-64 `Math.log` and `Math.exp` intrinsics, for bit-exact logarithms in SimOxide's exact mode |
| `simoxide-emf-core` | EPL-2.0 | EMF's core without storage: dense ids (`PackageId`, `ClassId`, `FeatureId`, ...), the `MetaRegistry` (dynamic, or seeded from generated tables: `seed`, `MetaRegistry::from_static`), `Datum` (feature values with Java's box kinds and Java `equals`), the `ModelStore` trait with EMF's write semantics and its contract test suite, `MetaOperation` |
| `simoxide-emf` | EPL-2.0 | the EMF graph (`Graph`, a `ModelStore`); Ecore built in, with the behaviour of its generated classes; `.ecore` registration and metamodel objects; XMI load and save byte for byte as EMF 2.41; resource sets, URIs, fragments, proxies; data type conversion; the change journal and id policies; the canonical dump and the Eclipse suite's comparer |

The licences and the opt-in features are explained in `LICENSES` (sections 4 and 7) and on
[Licensing](../qvto/licensing.md).

No EPL crate depends on an opt-in crate except through a feature. The QVTo crates never depend
on SimOxide's model or simulator crates. The QVTo crates import `simoxide-emf-core` and
`simoxide-emf` under their former names, `qvto_model` and `qvto_emf`, through Cargo's package
rename.

## The shared graph

`simoxide_emf::Graph` holds the objects of every metamodel of a run: PCM, the runtime measurement
model, SPD, Ecore, QVTo's intermediate classes. References may go between them.

- **Registry.** SimOxide's generated PCM tables (`simoxide-model/src/meta/generated.rs`, written
  by `tools/gen_meta.py`) are a `seed::StaticPackages`. They are registered first, so every table
  index is the registry id: `simoxide_model::meta::ClassId` *is* `simoxide_emf_core::ClassId`.
  SimOxide's static lookups (`c.def()`, ...) are extension traits
  (`simoxide_model::meta::prelude`). Ecore and the metamodels loaded at run time follow. The
  registry sits behind an `Arc`, shared by the compiled programs, all runs and forks. Adding a
  metamodel copies it on write.
- **Objects.** Each object has one slot per feature, in `eAllStructuralFeatures` order. The
  objects are stored in chunks whose frozen prefix is shared (`Graph::freeze`): cloning a graph
  for a fork is cheap, and a write copies only the chunks it touches. `Graph` is
  `Clone + Send + Sync`. `CompiledModel` holds it and stays `Send + Sync`, which a compile-time
  assertion in `simoxide-sim` checks.
- **Writes.** The `ModelStore` operations have EMF's semantics: defaults, `isSet`, uniqueness,
  containment moves, opposites, container references, roots, `EcoreUtil.delete`, `setEList`.
  Loaders write through separate operations (`load_ops`) that the journal does not record.
- **Journal.** When it is on, the graph records every effective change of its EMF operations,
  side effects included: `Set` with the values on both ends of opposites, `Added` and `Removed`,
  container and root changes, `Deleted`. SimOxide turns a journal into the simulator's change set
  ([QVTo in SimOxide](../qvto/simoxide.md)).
- **Ids.** An `IdPolicy` gives new objects of PCM's `Identifier` class (or another target class)
  EMF-like UUIDs from a seeded generator. The generator's state lives in the graph, so it is
  cloned and snapshotted with it.
- **Loading.** Two loaders write the same graph. SimOxide's PCM loader (`simoxide-model`:
  `xmi.rs`, `load.rs`) keeps the rules of EMF 2.33, the version of the SimuLizar 5.2.2 product,
  plus SimOxide's diagnostics, parse cache and in-memory loading. `simoxide_emf::xmi_load` is
  the general XMI loader with EMF 2.41's rules, which the QVTo side uses. Both are checked
  against their EMF version.
- **Canonical dumps.** There are two formats with two committed EMF oracles. SimOxide's
  (`simoxide-model/src/canon.rs`) has goldens from EMF 2.33 (`reference/oracles/pcm-model`).
  `simoxide_emf::canon` is QVTo's strict comparison format, and the Java reference runner writes
  the same format.

## Verification

`cargo test-fdn` runs the foundation crates' tests (release):

| Test | What | Result |
|---|---|---|
| `simoxide-emf/tests/suite_models.rs` | the 546 model files of the Eclipse QVTo test suite: load errors, XMI save with the resource's options, canonical dump after `resolveAll`, against EMF 2.41 | 544 equal (save byte for byte); 2 excluded (instances of QVTo's AST metamodel, which EMF itself stores in the wrong slots) |
| same, PCM part | 640 PCM-side files: SimOxide's corpus, Palladio's default models, Slingshot and SPD examples, the SPD and SimuLizar metamodels | 640 equal (needs `target/pcm`, [Reference material](../qvto/development.md#reference-material)) |
| `tests/scripts.rs` | 300 random edit scripts (15 321 operations, with wrong types, nulls and bad indexes) on dynamic EMF objects, then saves with two option sets | every result, final state and save equal to EMF |
| `tests/compare.rs` | the suite's lenient comparer on 1 663 model pairs | 1 662 verdicts equal to Java's `TreeComparator` (one pair skipped: Java's comparer throws) |
| `tests/contract.rs`, `materialize.rs`, `registry.rs` | the `ModelStore` contract, with the metamodel built in code and loaded from `.ecore`; metamodel objects and registration | pass |
| `tests/journal.rs` | what the journal records, and nothing while it is off | pass |
| `simoxide-jcompat-exact/tests/closed_form.rs` | SimOxide's closed-form `HashMap` order against the full `JavaHashMap` | pass |

The oracle (`crates/foundation/simoxide-emf/oracle`: `CanonDump`, `EmfOracle`, `ScriptRunner`)
runs on the QVTo reference runner's jars. `crates/foundation/simoxide-emf/README.md` gives the
commands that record its data again.

SimOxide's side of the graph is guarded by its own tests: the EMF canonical-dump goldens of
`simoxide-model` (165 goldens), `load_all`, `semantics`, `xmi-cases` and `memory`, and the
[guardrails](./contributing.md#guardrails). The golden hashes of the exact build must not change.
A change to the graph or the loader also runs `load-bench` ([Benchmarking](./benchmarking.md)),
because loading matters to optimisation loops that load a model per candidate.
