# Integrating qvto-rs into SimOxide

State: 2026-10-17, after milestone Q6. This is the plan for running SimuLizar's reconfiguration
rules (and Slingshot's SPD transformations) inside SimOxide, option D of
`SIMOXIDE-self-adaptation-options.md` plus the engine that option A/B needed. The QVTo side is
done; what is left is SimOxide's side.

## 1. What exists now

**The engine** runs QVTo as Eclipse does: 494 of 494 runnable Eclipse test cases and 24 of 24
SimuLizar/SPD corpus cases equal the Java reference strictly (models, logs, status, stack
traces). A rule compiles in about 1 ms and runs in microseconds (below).

**The adapter** (`crates/qvto-simoxide`, a crate of its own next to the qvto-rs workspace):

| Part | What it does |
|---|---|
| `registry` | the `MetaRegistry` of SimOxide's generated tables, **with SimOxide's ids**: `ClassId(i)`, `FeatureId(i)`, `EnumId(i)`, `PackageId(i)` mean the same as in `simoxide_model::meta`. Ecore follows; metamodels loaded later after that. Equal to the registry built from the product's `.ecore` files (35 packages, 299 classes, 520 features, every property). |
| `SimStore` | a `ModelStore` over `simoxide_model::raw::Graph`: handles are SimOxide's `ObjId`s, values are read and written in `Obj::slots` in place, no copy. EMF's semantics (defaults, `isSet`, uniqueness, containment, opposites, container references, roots, `EcoreUtil.delete`) ported from `qvto_emf`, checked by the contract suite and by 300 random PCM scripts against `qvto_emf` (about 24 000 operations, all results and final states equal). |
| `Session` | what lives as long as the model: the registry, metamodel objects for `eClass()` (created from the registry, `qvto_emf::ResourceSet::materialize`), a `qvto_emf` graph for objects of other metamodels (the PRM, SPD models, intermediate-class instances) that may refer to graph objects, the resource table, the journal, the id policy. |
| `Journal` | every change of a run as EMF notifications report it (created, set, unset, added, removed, replaced, moved, container, root added/removed, deleted), side effects included (both ends of opposites, old containers), plus a per-object summary: the syncers' input. |
| `IdPolicy` | no ids for new objects (dynamic EMF, the corpus's reference) or EMF-style UUIDs from a seeded generator (what generated PCM code does, reproducibly). |

**SimOxide changes** (branch `qvto-adapter` of SimOxide, two commits, additive, SimOxide's 215
tests pass): `tools/gen_meta.py` writes `src/meta/generated_ext.rs` (multiplicities,
ordered/unique/changeable/unsettable, interface flags, complete supertypes, data types, classifier
order, `EOperation` signatures, the `platform:/plugin` location of each package; `generated.rs` is
regenerated byte for byte unchanged) and `raw::Graph::add_object(class, resource)`.

**Results on SimOxide-loaded models**: the 24 corpus cases (SimuLizar's `QVToReconfigurationTest`
rules, the load-balancer and power-consumption examples, SPD's `MainTransformation`) on PCM
models loaded by `simoxide_model::Loader` give the Java runner's outputs, logs and status.
Per rule execution on SimOxide's MediaStore model (release, median of 300 runs, journal on;
`cargo run --release --example bench`):

| rule | 6 containers | 100 | 1 000 | vs `qvto_emf` store |
|---|---:|---:|---:|---:|
| power-consumption `scaleUp`, fires | 7.8 µs | 83 µs | 0.86 ms | 1.06-1.12x |
| `scaleUp`, below threshold | 3.2 µs | 3.5 µs | 3.4 µs | 0.9-1.0x |
| power-consumption `scaleDown`, fires | 6.9 µs | 50 µs | 0.54 ms | 0.94-1.0x |
| read-only scan of the whole model | 87 µs | 97 µs | 198 µs | 0.92-0.99x |

Eclipse needs 4.7-7.7 ms for a corpus rule run (warm). Creating a session (registry, metamodel
objects, PRM metamodel) takes 2.4 ms, compiling a rule 1 ms, both once per simulation.

**The runtime flow** (`cargo run --example runtime_flow`): SimOxide loads MediaStore; the
session loads SimuLizar's runtime-measurement metamodel from embedded `.ecore` text; an
autoscaling rule (clone a container above 80 % utilisation after warm-up, remove the newest
clone below 30 %) is compiled once with `getSimulationTime()` bound to a clock; ten
measurements are written into the PRM model (whose measurement refers to a measuring point of
SimOxide's graph), the rule runs on the graph each time (17-70 µs), the journal goes to a stub
syncer that names the SimOxide work (new container: resources, routes, allocation lookup;
removed container: SimuLizar keeps simulating it), and SimOxide's typed model rebuilt from the
changed graph validates without errors (0.2-0.5 ms per rebuild).

## 2. The API boundary

```
SimOxide                                  qvto-simoxide / qvto                 
---------------------------------------   ----------------------------------------
raw::Graph (per run, mutable)  <------->  SimStore (view: &mut Graph, &mut Session)
meta tables + extension tables  ------->  registry (ids equal), materialized objects
measurement values (PRM writes) ------->  PRM objects in the session (Session/SimStore API)
simulation clock                ------->  Natives: getSimulationTime
rule files (fixed order)        ------->  qvto::compile_with_metamodel (once)
reconfiguration process         ------->  Vm::run_transformation per rule
syncers                         <-------  Journal (per rule run)
```

- **Ownership.** SimOxide owns the graph; a `SimStore` borrows it for one rule run (cheap to
  create). SimOxide must not change the graph while a store exists, and must expect new
  objects, detached objects (no container, no resource) and objects in a `qvto:/created`
  resource after a run.
- **Ids.** Graph object handles are `raw::ObjId`s, metamodel ids are SimOxide's; objects of
  other metamodels have handles from `EXT_BASE` (2^30) on and never appear in the graph.
- **Not supported across the two homes**: a graph object referring to an object of another
  metamodel; containment or opposites between the homes. No PCM, PRM or SPD model needs them.
- **Dependency direction.** SimOxide depends on `qvto-simoxide` (and through it on `qvto`,
  `qvto-emf`, `qvto-model`) behind a cargo feature (`reconfiguration`), by path or git; all
  EPL-2.0. The adapter stays in qvto-rs because its tests use qvto-rs's corpus and testkit.
  When the branch `qvto-adapter` is merged, its `Cargo.toml` path changes from
  `../../../simoxide-qvto/...` to SimOxide's main checkout.

## 3. What SimOxide needs (option D)

### D1 A mutable model per run

Today `CompiledModel` (`simoxide-sim/src/ir.rs`) is built once and shared immutably by all
runs (`Send + Sync`, `run_batch`). Reconfiguration needs per-run state:

- the run owns a clone of `model.graph` (MediaStore: 1 220 objects; cloning is cheap compared to
  a run) and a **mutable overlay** of the compiled parts that reconfiguration invalidates:
  `resources`, `container_res`/`container_res_dense`, `container_simulated`, `link_res`,
  `route_res`, `links`, `finalise_order` (Java `HashMap` order, recomputed as SimuLizar's
  resource registry would iterate after the insertion), `alloc` and `ac_paths[*].container`,
  `prov_deleg`/`req_conn`/`seff_for` when the system or repository changes, and `progs` (StoEx
  programs) for changed specifications;
- runs without reconfiguration rules keep using the shared `CompiledModel` unchanged (no cost
  for them); with rules, the overlay starts as a copy-on-write view.
- New dense indexes are appended (new resources, containers); removed elements are
  tombstoned, so indexes held by in-flight requests stay valid.

### D2 Runtime measurement values (the PRM)

SimOxide's PRM recorders (`prm_tuple`, `prm_write`, MEAS-7.2) only trigger the process today.
They must store the value: one `RuntimeMeasurement` per (measuring point, measurement
specification) in a PRM resource of the session, created when the recorder is attached
(SimuLizar's `PRMRecorder`), its `measuringValue` set at every write. The measurement refers to
SimOxide's measuring point and specification objects (mirrors); the PRM metamodel is embedded
(`crates/qvto-simoxide/data/runtimemeasurement.ecore`).

### D3 The reconfiguration process

`reconf_run` (`sim.rs`) runs the rules: compiled once at simulation start, in a fixed order
(SimuLizar loads the rule folder in file-system order; SimOxide sorts by file name and documents
it). Each rule's parameters are bound by model type as `AbstractQVTOExecutor`/`QVToModelCache`
do: the PRM's measurements as `in`, PCM models by nsURI as `inout`, the monitor repository; a
rule "fails" through `assert fatal` (severity ERROR), which SimuLizar treats as "not applied".
The journal of the successful rules goes to D4; `Reconfiguration Time` tuples and the container
count series (MEAS-7.3) follow SimuLizar.

### D4 Syncers from the journal

| Change (journal) | SimuLizar | SimOxide |
|---|---|---|
| `ResourceContainer` added to a resource environment | `ResourceEnvironmentSyncer`: simulated container with its active resources | create resources (indexes appended), `container_simulated`, routes; count series |
| `ProcessingResourceSpecification` rate, replicas, scheduling | syncer updates the resource | recompile the StoEx, update the resource |
| `LinkingResource` added / latency, throughput | syncer | link resources, route table |
| container removed | **not handled**: it keeps simulating | compat mode: the same (keep simulating); fixed mode: drain and remove |
| `AllocationContext.resourceContainer` changed | **ignored** (`AllocationLookupSyncer`) | compat: ignore; fixed: update `alloc` |
| `AllocationContext` added | lookup entry added | `alloc`, `ac_paths` |
| `AllocationContext` or composite component removed | crashes | compat: report as SimuLizar's error; fixed: remove |
| system, connectors, SEFFs, StoEx in SEFFs | read live by the interpreter | invalidate `prov_deleg`, `req_conn`, `seff_for`, `code`, `progs` |

The journal gives the changed objects and features; the mapping back to typed entities uses the
typed model's `obj` fields (every entity keeps its `ObjId`). A first version may rebuild the
typed model and recompile after a reconfiguration (0.2-0.5 ms for MediaStore's typed model) and
diff it against the running one; the incremental syncers replace that where it matters.

### D5 Exactness

New PCM objects need ids (`IdPolicy::Uuid { seed }`); byte equality with SimuLizar needs a
reference runner patched for deterministic `EcoreUtil.generateUUID`. New resources and
processes shift process ids and event order; that follows from the model changes and is
reproducible once the ids are. Rule order and the `HashMap` orders SimuLizar iterates
(resource registry, model cache) are the other sources; both are reproducible.

### D6 Blackboxes

`getSimulationTime` is a closure over SimOxide's clock (`qvto::blackbox::palladio::
register_simulation_time`). The stereotype library (`ProfilesLibrary`, EMF Profiles) is used by
the SPD helpers and by SimuLizar rules of the action interpreter, not by the corpus rules; it
needs stereotype applications in the session (an EMF Profiles model) if such rules are wanted.

## 4. Plan and estimates

Estimates are human developer time, for someone who knows SimOxide.

| Step | Work | Estimate | Done when |
|---|---|---|---|
| 1 | Merge SimOxide's `qvto-adapter` branch; `reconfiguration` cargo feature with the dependency on `qvto-simoxide` | 0.5 day | SimOxide builds with and without the feature |
| 2 | D2: PRM values in the session, written by the PRM recorders | 3-5 days | the corpus PRM files can be replaced by recorded measurements |
| 3 | D3: rules loaded, compiled, bound and run by the reconfiguration process; journal collected | 3-5 days | the corpus rules run inside a simulation; their journals match the corpus results |
| 4 | D1: per-run graph and overlay of the compiled model, with full rebuild-and-diff as the first syncer | 2-3 weeks | a rule that adds a container changes the simulation; runs without rules are not slower |
| 5 | D4: incremental syncers for the table above, compat (SimuLizar's gaps) and fixed modes | 2-3 weeks | SimuLizar's reconfiguration examples (load balancer, power consumption) against a patched SimuLizar, statistically; exactly with D5 |
| 6 | D5: deterministic ids in the reference runner; exact comparison of reconfiguring runs | 1 week | byte-equal traces on the examples |
| 7 | Optional: SPD (Slingshot) semantics on top (triggers, constraints) using `MainTransformation` | 3-5 weeks | the Slingshot SPD examples |

Total for SimuLizar parity (steps 1-6): about 6-9 weeks; the engine side is not on the
critical path any more (the original option D estimate of 4-8 weeks assumed the QVTo part
separately).

## 5. Risks

| Risk | Mitigation |
|---|---|
| The hot path assumes fixed dense indexes (`container_res_dense`, `route_res`) | append-only indexes with tombstones; rebuild the dense tables at reconfiguration (rare events) |
| SimuLizar's syncer gaps are behaviour to reproduce, not bugs to fix | compat and fixed modes, as SimOxide already does for other quirks |
| Exactness against SimuLizar needs a patched reference | deterministic UUIDs in both; compare statistically until then |
| A rule changes something SimOxide precomputed and no syncer handles | the journal names every changed feature; unknown changes fall back to rebuild-and-diff or an error |
| SimOxide's main metamodel tables miss generic supertypes (`IntSample` etc. extend `Sample<T>`) and `PCMBaseClass`'s explicit `EObject` | the adapter uses the extension tables; SimOxide's loader would not know `Sample`'s features on those classes (not seen in any corpus model) |
| Objects of other metamodels cannot be referenced from the graph | not needed by PCM, PRM, SPD; a model needing it would get an `Unsupported` error (the VM's `invalid`) |

## 6. Open points of the adapter

- `xmi:id`s of detached graph objects are kept (EMF drops them from the resource's ID map).
- Journal entries of objects of other metamodels are the operations as called (no side effects
  on other objects); none of them are PCM objects.
- `EcoreUtil.delete` searches all resources (minus metamodels): O(model size) per delete, as in
  EMF.
- Materialized metamodel objects have no `EAnnotation`s (no OCL bodies or derivations; SimOxide's
  metamodels have none that QVTo evaluates).
