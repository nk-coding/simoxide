# qvto-testkit

The conformance and differential harness: the Eclipse QVTo test suite and the SimuLizar/SPD
corpus as runnable cases, the Java reference runner's results for them, the interface the
qvto-rs engine implements to run under the harness, the comparisons and the scoreboard
(`qvto conform`).

```sh
qvto conform                                  # scoreboard of the engine (qvto; --engine qvto-fast|stub) on all cases
qvto conform --suite eclipse --prefix interpret_ --report report.md --tsv report.tsv -v
qvto conform record [--suite eclipse|corpus]  # Java runner: refresh the fixtures (5 runs, ~10 s each)
qvto conform --engine replay:target/qvto-testkit/java   # Java's own results through the Rust side
qvto conform --suite spd --compare-unstable   # also compare what varies between Java runs
qvto conform record --det                     # the det Java runner (insertion order): java-<suite>-det.txt
qvto conform --engine qvto-ordered            # ordered mode against the det fixtures
```

Prerequisites: the reference checkout (`reference/README.md`), the runner built
(`reference/runner/build.sh`; `record` builds it), and for the corpus the PCM metamodels:
`../foundation/simoxide-emf/tools/pcm-setup.sh target/pcm` (run here; its `pcm.conf` holds
absolute paths, so once per target directory). Overview of the oracles and the current results:
`docs/qvto/conformance.md` (the documentation site).

### Case files

Blocks of `key value` lines (value: the rest of the line), `#` comments. The Java runner
(`reference/runner/src/qvtorun/Job.java`) reads the same format; keys it does not know are for
the Rust side.

```text

qvto <transformation>
in <model>                         for the next in/inout parameter (positional)

mmfile <.ecore>                    loaded and registered in the resource set (includeMetamodelFile)

```

## Java side

`reference/runner` (`Batch.java`, `CaseRunner.java`): one JVM runs a whole case file, each case
on a fresh thread with a deadline; ~8 s for the 494 Eclipse cases. It sets up what the Eclipse
test environment provides:

- EMF's `plugin.xml` registrations through EMF's standalone `ExtensionProcessor`, with the test
  bundle and the samples plugin on the classpath: the generated packages (`testqvt`,
  `generics`, `simpleuml`, `rdb`, QVTo's own), the dynamic packages, `platform:/plugin` maps;
- the test bundle's Java classes compiled from the reference checkout: blackboxes
  (`bbox/*`, `TestBlackboxLibrary`, the `parserTestData/sources/*/src` folders of its
  `build.properties`, the bug577992/bug507955 libraries, the buddy bundle), generated packages,
  the suite's comparer;
- import resolution against the bundles' source containers (`qvtTransformationContainer`), as
  `PlatformPluginUnitResolver` does under OSGi (standalone QVTo resolves imports only from the
  importing file's folder, while the suite imports `models.<case>.<Unit>`);
- the resource set, parameter binding, blackbox registration, configuration properties and
  output comparison of `TestQvtStandaloneExecutor`, the log (`WriterLog`) and session options of
  the workspace drivers.

Per case it writes `result.txt`, `out.jsonl` (canonical dump of the out/inout extents, proxies
resolved, each extent as resource `extent<i>.xmi`), `log.txt`, `stack.txt`, `diag.txt` (compile
problems with line, offset, length; the diagnostic tree), `idtape.tsv`, and with `--save-xmi`
the extents and the models as the run left them (for `JavaReplay`). Absolute paths in texts
become `${root}`.

**Result: all 494 runnable Eclipse cases and all 24 corpus cases pass on the Java side** (the
drivers' checks, evaluated in Java with Eclipse's own comparer).

`qvto conform record` runs the batch five times: the first run's results go into the fixture
bundle (small files without timings; tapes and XMI stay in the cache `target/qvto-testkit/java`),
the reruns cycle through constant identity hashes (`-XX:hashCode=2`), sequential ones
(`-XX:hashCode=3`) and HotSpot's default, and outputs that differ in any rerun are marked
`unstable` (8 Eclipse cases: identity-hash order in 6 dumps, `Class@hash` and elapsed times in 2
logs; 2 corpus cases). Detection is probabilistic: a set of two identity-hashed elements keeps
its order in a rerun with probability 1/2 (`qvto conform record --runs N`). With `--only` or
`--prefix`, the recorded cases replace theirs in the existing bundle and cache. The runner runs
each case on a thread with a 512 MB stack, so that QVTo's own call depth limit (1 000) applies
before a JVM `StackOverflowError` (a default thread stack overflows at about 740 calls).

The runner also has a benchmark mode (`qvto-run --bench WORKLOADS --out RESULTS.tsv`,
`Bench.java`) for `qvto bench --java` (`qvto-cli/README.md`): workloads in the case
format with `bench <key> <value>` lines, compiled K times and run in fresh or series mode with
the same protocol as the Rust side. `QVTO_NICE` sets the runner's niceness (default 19;
benchmarks run it at 0, pinned with `taskset`).

## Engine interface

```rust
pub trait Engine {
    fn name(&self) -> &str;
    fn run(&mut self, env: &CaseEnv) -> Outcome;
}
```

`CaseEnv` gives the case, the QVTo root, the metamodel configuration and a resource set
set up like the Java side's (`env.resource_set()`). The engine compiles `env.transformation()`
(only that for compile-only cases), binds `case.inputs` positionally to the in/inout
parameters, applies configuration properties, blackboxes and session options, runs, and returns
an `Outcome`: load severity and problems, execution severity/code/message, terminating
exception class, printed QVT stack, log, trace-record count, and `Outputs` (the extents as
resources `extent<i>.xmi` in a qvto-emf `ResourceSet`, plus the other model resources for
`dump models`). `StubEngine` answers `NotImplemented` for every case; the engine itself is
`qvto-cli/src/engine.rs` (`qvto`, `qvto-fast`): it resolves imports like the Java
runner (bundle source containers, then the case's Java blackbox units from
`qvto-types/data/blackboxes.tsv` — the test bundle's for `bundle-blackboxes`, the case's own
registrations, Java classes by name — as the analyser's oracle harness does), loads the
metamodels the units name (plus Ecore's own objects, the QVT metamodel's second registry key
and the EMF jars' `XMLType`/`XMLNamespace`/`Change`), compiles with the metamodels'
EOperations, binds the inputs (`getResource`: a registered metamodel file given as input is
that resource), replays the Java run's identity hashes when the tape is cached (inputs by key,
created objects in the recorded thread's draw order), runs with the native blackboxes of
`qvto-cli/src/bbox.rs` (QVTo's `Strings`/`emf.tools`, the test bundle's Java libraries
ported, the runner's `ProfilesLibrary` stub), and puts the extents into `extent<i>.xmi`.
`QVTO_SHOW=1` prints each case's outcome, log and dump.

## Verdicts

Per runnable case: the driver's checks on the outcome (the Eclipse verdict: `pass-lenient` if
only these pass) and the strict comparison with the Java fixture (`pass`): load, severity, code
and exception; canonical dumps (order, values, reference targets); log; stack; problems by
severity and line. Unstable aspects (those that differed between the recording's Java runs)
are not compared unless `--compare-unstable` is given (the engine replays the recorded run's
identity hashes, so it should reproduce that run); QVTo's in-memory extent resources
(`extent:/N`) are compared renumbered by first appearance, as Eclipse numbers them with a
JVM-wide counter (the Java side's numbers depend on the cases run before). Other verdicts: `fail`, `unsupported`,
`not-implemented`, `crashed`, `java-fails` (harness problem), `java-fails-equal` (the Java
runner fails the checks too, and the engine equals it strictly; the `det` runner),
`unrunnable:<category>`. The
report tallies by driver, kind and feature tag (`-v`).

Check of the harness itself (`tests/harness.rs`): replaying Java's saved outputs through the
Rust side (qvto-emf loads the XMI, the Rust checks, the Rust canonical dump) gives `pass` on all
494 Eclipse cases and on 22 of the 24 corpus cases; the other two pass leniently because QVTo
leaves objects created without a container in its internal `extent:/N` resources (contained
across resources), which a saved XMI cannot hold.

- Slingshot's SPD `MainTransformation` (with its libraries and sub-transformations) on the minimal example, with the

A chained state is a case's outputs, saved by the Java runner with the `det` ordering rule (so
the state is reproducible), with the extents renamed to the model files, ids `_q1_<state>_<n>`

`RequiredDelegationConnector`s SPD's constructor leaves without parent point to removed
assemblies after a scale-in). Every case has `resolve-all`.

Path coverage: `QVTO_COVERAGE=DIR qvto conform --suite spd` writes the operations each case
entered (`DIR/<case>.tsv`: kind, `Module::Context::op/params (unit:line)`, entries, entries whose

the 17 units are reached, every operation in `MainTransformation`'s call graph (the other 32 are
helpers no reachable operation calls; DESIGN-SPD §5.5 "Q1 as built").

Result: compat 47 of 47 strictly equal to the Java runner, also with `--compare-unstable`; ordered
mode 47 of 47 equal to the `det` runner, also with `--compare-unstable`.

(`reference/slingshot`, `spd.jsonl`) on one in-memory copy of the models and compares each
adjustment's outcome and model summary (containers, links, allocation, target-group elements, in
order): 13 of 13; its unit test runs it with `cargo test-qvto`.

## The `det` Java runner

The Slingshot reference runner's `det` mode makes QVTo's and OCL's `HashSet`/`HashMap`
`LinkedHashSet`/`LinkedHashMap` (its seed agent, an ASM rewrite at class-load time). `qvto
conform record --det` and `qvto conform java --det` run the QVTo Java runner with the same agent
(`-javaagent:seed-agent.jar=ordered,qvto`; `reference/oraclekit/seed-agent.sh` builds it,
`QVTO_DET_AGENT` names another jar) and write `fixtures/java-<suite>-det.txt` and the cache
`target/qvto-testkit/java-det/<suite>`. `--det` makes the scoreboard compare with those fixtures;
`--engine qvto-ordered` implies it. Results: every case of every suite equal, 6 of them with
verdict `java-fails-equal` (the ordering rule turns OCL `Set`s into `LinkedHashSet`s, which OCL
takes for OrderedSets, so `bug467600_*` fail their own assertions in Java; ordered mode fails
them identically). The verdict `java-fails-equal`: the Java runner fails the Eclipse checks, and
the engine's outcome equals it strictly (counted apart, not as a pass).

## Identity-hash tape

`idtape.tsv` per case (cache only, ~11 MB for the suite): the case thread's first two identity
hashes (`seed`, the first thing the case's thread does; the batch sets the environment up
before), then for every object of the inputs, the outputs and their metamodels its identity hash
and whether the run assigned it (read from the mark word through `sun.misc.Unsafe` before the
tape asks for the hash), keyed like the canonical dump (`<label>#<path>`,
`mm:<nsURI>#<fragment>`). The objects of the input resources come first, as `pre` lines keyed by
their path *before* the run (a run that reorders an inout list moves them); `obj` lines are the
others. HotSpot's default hash is a per-thread xor-shift
sequence; `idhash::XorShift::recover` reconstructs the thread's state from the seed (every tape
since the seed is taken first), and every model-object hash the run assigned is found in that
sequence (the engine searches the first 2 000 000 draws; compiling the SPD transformations alone
takes about 10 000). The engine assigns the recorded hashes by object key to the objects that
existed before the run, and the hashes of the other objects (the run's own) in the order of the
sequence; this needs the engine to request identity hashes of created objects where Java does,
including Java's side effects (DESIGN §12 SPD-Q1-2). `QVTO_TAPE_DEBUG=FILE` writes both orders
(Java's tape objects by sequence position, the engine's draws) for comparing. Not on the
tape: objects that end up in no extent (intermediate data, discarded objects, `Status`,
exceptions) and metamodel objects hashed on earlier threads (their recorded values are still
exact).

## Fuzzing

The `qvto fuzz` commands (`qvto-cli/src/fuzz.rs`, `robust.rs`; DESIGN §12 Q7-1 to Q7-3):

| Command | What it does |
|---|---|
| `qvto fuzz expr [--seed N] [--minutes M \| --batches B] [--cases C] [--stmts S] [--out DIR]` | batches of transformations of labelled expression statements (`log('@eN@', ...)`) over a generated model, run in one Java batch and in the engine; differences per statement (value, value-context, sema) are minimised over the expression tree and written to `DIR/findings/` |
| `qvto fuzz prog ...` | generated transformations (mappings with guards, `inherits`/`disjuncts`, resolve and late resolve, intermediate classes, helpers and queries, `try`/`raise`, module properties) over generated models, compared strictly (outputs, log, errors) |
| `qvto fuzz recheck DIR...` | runs the saved findings again (after a fix) |
| `qvto fuzz corpus --cases FILE [--out DIR] [--only ID,...] [--reuse]` | compares compile problems (and, for run cases, the run) of a case file with the Java runner: `report.tsv`, `mismatches.tsv` |
| `qvto fuzz robust [--workers N] [--minutes M] [--mem-mb MB]` | the mutational robustness fuzzer: panics, aborts and hangs of the pipeline, inputs kept in `crashes/`; `robust-replay FILE` runs one input |

Both sides of `expr`/`prog` and of the `fuzz` suite run with constant identity hashes
(`-XX:hashCode=2`, `identity::Constant(1)`), so orders of hashed collections are compared too.
Campaigns are bounded and niced (`--minutes`, at most four workers on the shared machine).
External corpora: `reference/external/` (not committed; `SOURCES.tsv` lists repositories,
revisions and licences), cases generated by `python3 -I qvto-testkit/tools/gen_external_cases.py [--run]`.
